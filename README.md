# DNA Sequencing Request

A single-page DNA sequencing request application written in Nim using [Karax](https://github.com/karaxnim/karax). The UI follows a **Model → Update → View** architecture inspired by Lustre, while keeping Karax responsible for rendering and browser events.


## Features

- Project-level sequencing request form.
- Conditional project fields.
- Sample spreadsheet-style editor.
- Sample columns automatically change when project answers change.
- Add/remove sample rows.
- Download a CSV template matching the current sample columns.
- Upload a completed CSV and replace the sample table with its contents.
- Client-side CSV parsing and validation.
- Reusable validator procs for project and sample data.
- Client-side validation as inputs change.
- Tailwind CSS styling.
- No server is required for the UI itself.

Submitting a validated request sends the project details in the HelpSpot note and as a YAML attachment, with the currently visible sample columns in a CSV attachment.

Progress is saved in this browser's localStorage and restored when the page is reopened on the same origin. It is not shared across browsers or devices, and clearing browser site data removes it. Form contents remain accessible to anyone using the same browser profile; use Reset to remove the saved request on shared computers. Browser storage limits and privacy settings may prevent saving, in which case the page displays a warning.

## Architecture

The application intentionally separates state from rendering:

```text
User event
   ↓
Msg
   ↓
update(model, msg)
   ↓
Model
   ↓
view(model)
   ↓
Karax VDOM
```

`model.nim` contains application state and schemas. `update.nim` owns state transitions. `main.nim` renders the model and converts browser events into `Msg` values. `validators.nim` contains reusable validation rules, while `validation.nim` runs schema and cross-row validation. `io.nim` handles project serialization and CSV representation.

This makes the conditional behavior explicit: the project model determines `sampleColumns(project)`, and the view renders exactly those columns.

## Requirements

- Nim 2.x
- Nimble
- Karax 1.3+
- A static web server for serving `public/`

Tailwind is loaded from the Tailwind CDN in the `src/index.html` template. For a production deployment, the CDN can be replaced by a pinned/local Tailwind build without changing the Nim application.

## Build

Install the dependency and build:

```bash
nimble install karax
nimble buildWeb
```

The build copies the HTML template and creates:

```text
public/index.html
public/app.js
```

For local development, serve `public/` with any static HTTP server. For example:

```bash
python3 -m http.server 8080 --directory public
```

Then open `http://localhost:8080/`.

## Extending the project

### Add a project field

Add a `ProjectFieldDef` to `projectSchema` in `src/model.nim`. Supply its kind, default value, visibility predicate, and validators as needed. The generic update and view paths use its key automatically.

### Add a sample column

Add a `SampleColumnDef` to `sampleColumnSchema`. Sample storage, the table, and CSV import/export use its key automatically.

### HelpSpot submission

Set the HelpSpot base URL, category ID, and optional `reportingTags` in `config.ini` and run `nimble buildWeb` after changing them. Quote the URL and reporting tags in the INI file. The client appends the public `request.create` API path to the base URL and sends nonempty reporting tags as configured. These settings are included in the browser bundle and must not contain credentials or secrets.

Run `nimble testHelpSpot` to create a real, clearly labeled test request in the configured category, including YAML and CSV attachments. It uses Node.js 18 or newer and the same model update and HelpSpot client as the application. The test uses `helpspot-test@example.com` as a placeholder contact address; it cannot receive notification emails. The task exits unsuccessfully if the submission cannot be confirmed. Check HelpSpot for an existing test request before retrying after a network error.

Enable HelpSpot's public API and ensure the HelpSpot endpoint allows cross-origin requests from the application's origin, or serve the application through a same-origin reverse proxy. Category-specific required custom fields and attachment restrictions must also be configured in HelpSpot. A network or CORS error can occur after HelpSpot has received a request, so check for an existing request before retrying.

## Design principles

- Keep domain state independent of Karax.
- Make state transitions explicit through messages.
- Keep validation reusable and testable outside the view.
- Derive sample columns from project state rather than duplicating conditional logic in multiple views.
- Treat CSV import as a schema-checked operation: a CSV must match the current project configuration.
- Keep browser-only JavaScript interop isolated in `main.nim`.

## Schema-driven fields and columns

The form and sample table are defined by the schema in `src/model.nim` rather than by conditional logic embedded in the view.

`ProjectForm` and `SampleRow` are string tables keyed by schema keys. Checkbox values are stored as `"true"` or `"false"` after an update; an empty value is also treated as unchecked. Project defaults are defined with `defaultValue` in the schema. Values in hidden fields remain stored when visibility changes.

`projectSchema` contains `ProjectFieldDef` entries with a key, label, input kind, options, help text, and a `visibleIf` predicate. For example, `referenceName` is declared with `visibleIf: customReferenceEnabled`, so the view does not need to know why that field is visible.

`sampleColumnSchema` works the same way for sample columns. Each `SampleColumnDef` contains its key, display label, and `visibleIf` predicate. CSV generation and the table view both call `visibleSampleColumns(project)`, so the displayed columns and CSV schema cannot accidentally diverge.

To add a conditional sample column, add a `SampleColumnDef` to `sampleColumnSchema`:

```nim
SampleColumnDef(
  key: "my_column",
  label: "My column",
  visibleIf: assayIs(assaySingleCell)
)
```

For more complex conditions, the predicate can be written inline:

```nim
SampleColumnDef(
  key: "example",
  label: "Example",
  visibleIf: proc(project: ProjectForm): bool =
   project.field("assay") == $assaySingleCell and project.field("indexType") == $dualIndex
)
```

Both field and column definitions can list validators, for example `validators: @[required("Sample ID")]`. Define reusable validator procs in `src/validators.nim`; each accepts a string and returns an error message or an empty string. All listed validators run for visible fields and columns. Cross-row checks, such as duplicate sample IDs, remain in `src/validation.nim`.

Run the validation tests with `nim c -r --out:/tmp/seqrequest-test-validation tests/test_validation.nim`.
